# Effect Style Guidance

How we write TypeScript with [Effect 4](https://effect.website/) in the backend, the MCP servers, `protocol/` and `shared/node-config/`. The examples were typechecked against `effect` 4.1.2 under `strict`. In Effect 4, most modules that were separate `@effect/*` packages in Effect 3 live inside `effect` itself: `effect/ai`, `effect/http`, `effect/http-api` and `effect/sql`. Database drivers such as `@effect/sql-pg` and the model providers such as `@effect/ai-openai-compat` are still separate packages.

## 1. Use Effect.fn for functions returning Effects

Name the function with its service and method, so it appears as a span in traces.

### Do This

```typescript
const getProvision = Effect.fn("LegalText.getProvision")(function* (provision: ProvisionId) {
  const repo = yield* PassageRepo
  return yield* repo.findProvision("sf", provision)
})
```

### Don't Do This

```typescript
const getProvision = (provision: ProvisionId) =>
  Effect.gen(function* () {
    const repo = yield* PassageRepo
    return yield* repo.findProvision("sf", provision)
  })
```

## 2. Prefer generator syntax over pipe

### Do This

```typescript
const findProvision = Effect.fn("PassageRepo.findProvision")(function* (corpus: Corpus, provision: ProvisionId) {
  const rows = yield* Effect.tryPromise(() => query(sql, [corpus, provision]))
  if (rows.length === 0) {
    return yield* new ProvisionNotFound({ provision, corpus })
  }
  return yield* Schema.decodeUnknownEffect(Schema.Array(PassageRow))(rows)
})
```

### Don't Do This

```typescript
const findProvision = Effect.fn("PassageRepo.findProvision")(function* (corpus: Corpus, provision: ProvisionId) {
  return yield* Effect.tryPromise(() => query(sql, [corpus, provision])).pipe(
    Effect.flatMap((rows) =>
      rows.length === 0
        ? Effect.fail(new ProvisionNotFound({ provision, corpus }))
        : Schema.decodeUnknownEffect(Schema.Array(PassageRow))(rows)
    )
  )
})
```

### Exception: pass combinators to Effect.fn

Combinators passed after the generator wrap the whole function body, which is the right place for error mapping that applies to every step:

```typescript
const embed = Effect.fn("EmbeddingClient.embed")(
  function* (baseUrl: string, apiKey: Redacted.Redacted<string>, input: string) {
    // ...
  },
  Effect.catchTag("HttpClientError", (error) =>
    Effect.fail(new DownstreamServiceError({ status: 0, message: `Could not reach the embedding endpoint: ${error.reason._tag}` }))
  )
)
```

### Exception: use .pipe() for simple effects

```typescript
const recovered = getProvision(provision).pipe(Effect.catchTag("ProvisionNotFound", () => Effect.succeed([])))
```

## 3. Prefer Effect.tryPromise over Effect.promise

`Effect.promise` treats a rejection as a defect, so a failed query escapes the error channel.

### Do This

```typescript
Effect.tryPromise(() => query(sql, params))
```

```typescript
Effect.tryPromise({
  try: () => query(sql, params),
  catch: (cause) => new DatabaseError({ cause: String(cause) })
})
```

### Don't Do This

```typescript
Effect.promise(() => query(sql, params))
```

## 4. Use the strictest Schema type possible

Always prefer the most constrained schema that accurately models the data. This catches bugs at the boundary (tool-call arguments from the model, MCP tool results, database reads, API requests) rather than deep in the agent loop. A small model can and will produce malformed tool arguments; a strict input schema turns that into a typed error the model can correct.

In Effect 4, constraints are filters applied with `Schema.check`, named `is…` (`isGreaterThan`, `isBetween`, `isMinLength`, `isPattern`, `isUUID`).

### Numeric types: match the actual domain

```typescript
// IDs generated by the database (start at 1)
const PassageId = Schema.Int.pipe(Schema.check(Schema.isGreaterThan(0)))

// A count that cannot be negative
const NoticeCount = Schema.Int.pipe(Schema.check(Schema.isGreaterThanOrEqualTo(0)))

// A share between 0 and 1
const Share = Schema.Number.pipe(Schema.check(Schema.isBetween({ minimum: 0, maximum: 1 })))

// Bad: Schema.Number for a value you know is a whole number
noticeCount: Schema.Number
// Good:
noticeCount: NoticeCount
```

### String types: be explicit about emptiness and structure

```typescript
// Any string that must not be empty
const DocumentTitle = Schema.NonEmptyString

// A fixed set of values: Schema.Literals, not Schema.String
const Corpus = Schema.Literals(["sf", "ams"])
const Language = Schema.Literals(["en", "nl"])

// A structured string
const Sha256 = Schema.String.pipe(
  Schema.check(Schema.isPattern(/^[0-9a-f]{64}$/, { message: "Expected a lowercase hex SHA-256 hash" }))
)
const RunId = Schema.String.pipe(Schema.check(Schema.isUUID()))

// Bad:
language: Schema.String
// Good:
language: Language
```

### Nullable and optional fields: only where truly needed

Only reach for `Schema.NullOr`, `Schema.optional` or `Schema.optionalKey` when the field is genuinely nullable or optional in the data source. Do not use them defensively.

```typescript
const Citation = Schema.Struct({
  sourceTitle: Schema.NonEmptyString,
  provision: Schema.NonEmptyString,
  // A dataset has no effective date; a provision always has one
  effectiveDate: Schema.NullOr(Schema.String),
  sourceUrl: SourceUrl,
  archivedFileSha256: Sha256,
  language: Language,
  machineTranslated: Schema.Boolean
})

// Bad: nullable "just in case"
sourceTitle: Schema.NullOr(Schema.String)
```

### Arrays: constrain length where meaningful

```typescript
// A claim must have at least one citation
const ClaimCitations = Schema.Array(Citation).pipe(Schema.check(Schema.isMinLength(1)))
```

### Secret fields: use Schema.Redacted

When a schema decodes a field that must never reach a log line or a trace (an API key for a cloud model, a token), wrap it in `Schema.Redacted` at the schema itself rather than relying on every caller to wrap the decoded value.

```typescript
// Bad: a caller who forgets to wrap it can log it by accident
const TokenResponse = Schema.Struct({ access_token: Schema.String })

// Good: every consumer gets a Redacted<string>
const TokenResponse = Schema.Struct({ access_token: Schema.Redacted(Schema.String) })
```

### Avoid Schema.Any and Schema.Unknown at boundaries

`Schema.Any` and `Schema.Unknown` opt out of all validation. Only use them in truly dynamic contexts, and document why. MCP tool inputs and outputs are never one of them: every tool has input and output schemas in the server that defines it, published to clients as its `inputSchema` and `outputSchema`. The backend's pass-through of a tool result to the browser app is the one dynamic case: the browser decodes the citations in it with `protocol/`'s schema.

## 5. Use .make() for constructing schema-typed values

When constructing a value that matches a defined schema, use the schema's `make` instead of a raw object with `as const` assertions. `make` validates the value, so a bad citation fails where it is built rather than where it is read.

### Do This

```typescript
const citation = Citation.make({
  sourceTitle: document.title,
  provision: passage.provision,
  effectiveDate: version.effectiveDate,
  sourceUrl: document.sourceUrl,
  archivedFileSha256: version.archivedFileSha256,
  language: "nl",
  machineTranslated: false
})
```

### Don't Do This

```typescript
const citation = {
  sourceTitle: document.title,
  provision: passage.provision,
  effectiveDate: version.effectiveDate,
  sourceUrl: document.sourceUrl,
  archivedFileSha256: version.archivedFileSha256,
  language: "nl" as const,
  machineTranslated: false
}
```

Use `make` inside `.map()` when transforming rows into schema-typed arrays.

## 6. HTTP clients: check the status and use typed error classes

Model calls go through `LanguageModel` and `EmbeddingModel` from `effect/ai`, and MCP calls through `McpClient` from `effect/ai`, so hand-written HTTP clients should be rare. When one is needed (for example a source or service with no provider package), follow this pattern.

`client.execute` succeeds for **any** status; it does not fail on 4xx or 5xx. Always inspect `response.status` before reading the body, and map statuses to typed errors:

| Status | Error class | Meaning |
|---|---|---|
| 401 | `UnauthenticatedError` | Not authenticated: credentials missing or expired |
| 403 | `UnauthorizedError` | Authenticated but not permitted |
| 404 | `NotFoundError` | Resource does not exist |
| 400 / 422 | `InvalidRequestError` | Bad input; the caller must fix the request |
| 5xx | `DownstreamServiceError` | The dependency is broken or unavailable |

Define these once in a shared errors module; don't redefine them per client.

There are two failure modes, handled in different places:

- **Transport and decoding failures** fail with `HttpClientError`, whose `reason` says what went wrong (`TransportError`, `StatusCodeError`, `DecodeError` and others). Catch it with a combinator passed to `Effect.fn`, which wraps the whole function.
- **HTTP errors** (4xx and 5xx) mean the server responded and signalled failure. Handle them in the function body by inspecting `response.status`.

```typescript
const embed = Effect.fn("EmbeddingClient.embed")(
  function* (baseUrl: string, apiKey: Redacted.Redacted<string>, input: string) {
    const client = yield* HttpClient.HttpClient
    const response = yield* client.execute(
      HttpClientRequest.post(`${baseUrl}/embeddings`).pipe(
        HttpClientRequest.bearerToken(Redacted.value(apiKey)),
        HttpClientRequest.bodyJsonUnsafe({ input })
      )
    )
    if (response.status >= 400) {
      const message = yield* HttpClientResponse.schemaBodyJson(ErrorBody)(response).pipe(
        Effect.map((body) => body.message),
        Effect.orElseSucceed(() => `HTTP ${response.status}`)
      )
      if (response.status < 500) {
        return yield* new InvalidRequestError({ status: response.status, message })
      }
      return yield* new DownstreamServiceError({ status: response.status, message })
    }
    return yield* HttpClientResponse.schemaBodyJson(EmbeddingResponse)(response)
  },
  Effect.catchTag("HttpClientError", (error) =>
    Effect.fail(new DownstreamServiceError({ status: 0, message: `Could not reach the embedding endpoint: ${error.reason._tag}` }))
  )
)
```

When a second client needs the status mapping, extract it into one shared helper rather than copying the branches.

### Prefer Schema.decodeUnknownSync outside an Effect context

Outside an Effect generator (a plain `async` function, a synchronous utility), decode with `Schema.decodeUnknownSync(schema)(value)`, which throws a `SchemaError` with a readable message. Don't wrap `Schema.decodeUnknownEffect` in `Effect.runSync` for the same job: it adds a runtime call and says less about intent. Inside a generator, `yield* Schema.decodeUnknownEffect(schema)(value)` is correct.

## 7. Define domain errors with Schema.TaggedError

Use `Schema.TaggedError` for all expected (recoverable) errors. The `_tag` discriminant enables precise handling with `Effect.catchTag`, and the error is typed throughout the call stack. A tagged error instance can be yielded directly to fail.

```typescript
class ProvisionNotFound extends Schema.TaggedError<ProvisionNotFound>()("ProvisionNotFound", {
  provision: ProvisionId,
  corpus: Corpus
}) {}

class EmbeddingModelMismatch extends Schema.TaggedError<EmbeddingModelMismatch>()("EmbeddingModelMismatch", {
  configured: Schema.NonEmptyString,
  stored: Schema.NonEmptyString
}) {}

// In a generator
return yield* new ProvisionNotFound({ provision, corpus })
```

Never use plain `Error` subclasses or plain objects as typed errors; they can't be matched by tag.

### Tool errors are returned to the model

An MCP tool's expected errors (no data for a period, a provision not in this version) are returned as the tool's result, typed by the server (each server defines its own, following the [tool-error convention](./domain-driven-design.md#conventions-between-servers-and-the-backend)), so the model can say "no data" rather than guess. They are not thrown as transport failures. Tools are `effect/ai` `Tool` definitions served by `McpServer`; set `failureMode: "return"` on each, so a handler's typed error becomes the tool's result. See [Domain-Driven Design § Tool errors are results](./domain-driven-design.md#tool-errors-are-results).

## 8. Distinguish expected errors from defects

- **Expected errors** (`Effect.fail`, or yielding a tagged error): things that can legitimately happen, such as a provision not found, an unreachable server or a bad request. They appear in the `E` type parameter and callers must handle them.
- **Defects** (`Effect.die`): bugs and violated invariants. They bypass the error channel and are not part of the function's contract.

```typescript
// Expected: a normal condition
if (rows.length === 0) {
  return yield* new ProvisionNotFound({ provision, corpus })
}

// Defect: a condition that should never occur
if (candidates.length > CANDIDATE_POOL) {
  return yield* Effect.die(new Error("Candidate pool exceeded its limit; the query limit is a bug"))
}
```

A configured embedding model that differs from the stored one is an expected error (`EmbeddingModelMismatch`) that stops the server at startup, with a message saying which models differ.

### Handling errors: prefer catchTag over catch

`Effect.catchTag` handles one named error precisely. `Effect.catch` (Effect 3's `catchAll`) handles every expected error at once; use it only at a boundary where you genuinely need to collapse them.

```typescript
// Good: targeted recovery
yield* getProvision(provision).pipe(Effect.catchTag("ProvisionNotFound", () => Effect.succeed([])))

// Only at a boundary
yield* program.pipe(Effect.catch((error) => Effect.logError("Unhandled error", error)))
```

`Effect.catchCause` and `Effect.catchDefect` also swallow defects. Use them only at the outermost boundary (the `HttpApi` handler, the MCP request handler), never in domain code.

## 9. Define services with Context.Service

Effect 4 defines a service with `Context.Service` (Effect 3's `Effect.Service` and `Context.Tag`), and its layer with `Layer.effect`.

```typescript
class PassageRepo extends Context.Service<PassageRepo>()("PassageRepo", {
  make: Effect.gen(function* () {
    const sql = yield* SqlClient.SqlClient
    const findProvision = Effect.fn("PassageRepo.findProvision")(function* (corpus: Corpus, provision: ProvisionId) {
      // ...
    })
    return { findProvision } as const
  })
}) {
  static readonly layer = Layer.effect(this, this.make)
}

// Access the service in an effect
const repo = yield* PassageRepo
```

The model is the main case of one port with several adapters: the agent loop depends only on `LanguageModel`, and one layer, chosen by configuration, provides it (local runtime, same model in the cloud, or frontier). Never import a provider package from the agent loop or branch on the configuration inside it.

## 10. Add human-readable messages to Schema constraints

Give each filter a `message` so parse errors are actionable. This matters twice here: the message reaches developers in logs, and, for tool inputs, it reaches the model, which uses it to correct its next call.

```typescript
// Good
const SearchQuery = Schema.NonEmptyString.pipe(
  Schema.check(Schema.isMaxLength(500, { message: "A search query must be at most 500 characters" }))
)

// Bad: a generic parse error with no context
const SearchQuery = Schema.NonEmptyString.pipe(Schema.check(Schema.isMaxLength(500)))
```

## 11. Use branded types for domain IDs

When several ID types share a primitive type, use `Schema.brand` to make them nominally distinct. This prevents passing a passage ID where a provision ID is expected.

```typescript
const PassageId = Schema.Int.pipe(Schema.check(Schema.isGreaterThan(0)), Schema.brand("PassageId"))
type PassageId = typeof PassageId.Type

const ProvisionId = Schema.NonEmptyString.pipe(Schema.brand("ProvisionId"))
type ProvisionId = typeof ProvisionId.Type

// TypeScript rejects this:
const findPassage = (id: PassageId) => { /* ... */ }
findPassage(5) // Error: Type 'number' is not assignable to type 'number & Brand<"PassageId">'
```

Decoding with a branded schema produces the branded type, so no casting is needed.

## 12. Test with @effect/vitest

Write tests with `it.effect` from `@effect/vitest`, provide test layers in place of real adapters, and assert on typed errors with `Effect.flip` rather than `try`/`catch`. The agent loop is tested with a stub `LanguageModel` and stub tools; tool handlers are tested against a throwaway Postgres testcontainer, never a shared database.

## 13. Read the environment through one configuration module

Each node declares every environment variable it reads in one module: `backend/src/config/BackendConfig.ts`, and `src/<Node>ServerConfig.ts` in each MCP server (`SfDataServerConfig.ts`, `SfDocsServerConfig.ts`). Related variables are grouped into a `Context.Service` class whose static `layer` reads them once at startup with `Config`, through the node's `dotEnv(path).load`, which makes a missing or invalid variable a `ConfigFileError` naming it and the `.env` file. Each field is documented with JSDoc, since Effect 4's `Config` has no `withDescription`.

- **Nothing else reads the environment.** No `Config.String("…")` in a repo or handler, no `process.env`. Code that needs a value `yield*`s its config service, so what a node reads is listed in one place and a test provides it with `Layer.succeed`.
- **Variable names keep the node's short name** through `Config.nested` (`Config.nested("SF_DATA")` with `Config.Port("PORT")` reads `SF_DATA_PORT`). A variable another project reads for the same thing, such as `OLLAMA_URL`, is not namespaced.
- **One `ConfigLive` layer** in `Server.ts` merges the node's config layers and provides the `.env` provider to them.
- **A test pins the names** by reading every config service from `ConfigProvider.fromEnvRecord` with the names in `.env.example`. Use `fromEnvRecord`, not `fromUnknown`: only the environment providers join `nested` prefixes with `_`.
- **Settings that are not secrets or per-machine values** (model limits, tool prefixes, search settings) stay in the node's YAML files, decoded with a `Schema` into their own `Context.Service`.

```ts
// san-francisco/mcp-servers/data/src/SfDataServerConfig.ts
import { fileURLToPath } from "node:url"

import { Config, Context, Layer } from "effect"
import type { Redacted } from "effect"

import { dotEnv } from "@policyhuis/node-config"

/**
 * `san-francisco/mcp-servers/data/.env`, whose values take priority over the shell's. Every environment variable this
 * server reads is declared in this module, each group read once at startup into its service below.
 */
export const SfDataEnv = dotEnv(fileURLToPath(new URL("../.env", import.meta.url)))

/** The database this server reads. Environment: `SF_DATA_READER_DATABASE_URL`. */
export class DatabaseConfig extends Context.Service<
  DatabaseConfig,
  {
    /** The connection string of the read-only `sf_data_reader` role, which can read only the `sf_data` schema. */
    readonly readerUrl: Redacted.Redacted
  }
>()("sf-data/DatabaseConfig") {
  static readonly layer = Layer.effect(
    this,
    SfDataEnv.load(Config.all({ readerUrl: Config.Redacted("READER_DATABASE_URL") }).pipe(Config.nested("SF_DATA")))
  )
}

/** The HTTP server that serves the MCP endpoint. Environment: `SF_DATA_PORT`. */
export class HttpConfig extends Context.Service<
  HttpConfig,
  {
    /** The port to serve `/mcp` on, which the backend's `config/servers.yaml` names for `sf-data`. */
    readonly port: number
  }
>()("sf-data/HttpConfig") {
  static readonly layer = Layer.effect(
    this,
    SfDataEnv.load(Config.all({ port: Config.Port("PORT") }).pipe(Config.nested("SF_DATA")))
  )
}
```
