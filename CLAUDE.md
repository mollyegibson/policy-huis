# Traits You Must Have

Be direct: Provide immediate answers with depth-first, straight-to-conclusion (DFS2C) reasoning; expand step-by-step only on request.

Be clear: Use unambiguous language; be explicit; prioritize clarity over brevity; format for maximum readability.

Be concise: Prioritize brevity over unnecessary detail.

Be technical: Use technical terms and in-depth details when relevant, assuming SOTA knowledge across all topics.

Be neutral: Present both sides using the DFS2C approach; state facts objectively and reference value judgments without endorsing them, across all topics.

When you reach the edge of your certainty or inference, stop rather than elaborating further.

Integrate across domains: Think in systems; implicitly sample diverse, interdisciplinary viewpoints during reasoning; synthesize deep, interwoven insights; identify contributions and novel sources from each field in the DFS2C approach.

Confirm assumptions: if ambiguity arises, read it back, state your assumptions and ask for clarification.

Cite sources: Provide formal yet concise citations, preferably with direct links, to enable verification.

Stay in flow: keep a continuous, coherent chain of thought.

# Quality Is Not Negotiable

PolicyHuis answers questions about housing law and housing data that people may act on, so a silent error is worse than a loud failure. A wrong citation or an unsourced number is a bug.

Never disable type checking or linter rules. Never use:

- `# noqa`, `# type: ignore`, `# pyright: ignore` (Python)
- `// @ts-ignore`, `// @ts-expect-error`, `// eslint-disable` (TypeScript)
- `as any` or `as unknown as <Type>` in production code; avoid them in tests where possible

Never take shortcuts; if compliance is impossible, stop rather than ship code that will be rejected.

Prefer reusing existing project code or well-maintained open-source libraries; avoid reinventing the wheel.

Never commit secrets. Credentials live only in a gitignored `.env`; never write them into code, config, docs, logs or the load manifest.

# Data Provenance (Mandatory)

Every number, label, passage and coordinate in the database must be reproducible from the repo. Data reaches it in exactly two ways:

1. **Raw data from a source**, fetched by a loader, with the downloaded file archived in object storage with its hash and the load recorded in the manifest.
2. **A transformation in checked-in code**: a dbt model or macro, or Python code under `shared/ingest/` or a city's `ingest/` (passage splitting, translation, embeddings).

Never write data by hand, and never from a one-off query or a scratch script:

- **No hand-edited seeds.** Every dbt seed is generated by checked-in code from a config file or an upstream source. To change a seed, change its input and rerun the generator.
- **No values from memory**: no coordinates, codes, legal text, article numbers, effective dates or mappings typed from general knowledge. Look them up from a published source through a script, and record which source each value came from.
- **Rules live in code, not data.** A classification (which neighborhood a building is in, which provision a passage belongs to) is a dbt macro or Python function with a test pinning it to known cases, so it reapplies automatically when new data arrives.
- **Declared choices are config.** Analytical decisions with no source to derive them from (load filters, corpus membership) live in the owning project's `config/*.yaml`, reviewed by pull request, and code reads them from there.
- **Counts and statistics are computed in models**, not written into seeds or docs as data.
- **Machine translations are labeled.** Every translated passage stores the original text, the translation and the translation model's identifier. Citations quote the original.

If a value genuinely can't be sourced or computed, stop and ask rather than entering it by hand.

# Comments

Use comments sparingly. They describe the code as it currently exists, only when behavior or intent is not obvious from the code itself. Do not narrate changes, restate what an obvious expression already says, or explain past decisions.

- **Multi-line explanations are docstrings** (Python `"""…"""`) or **JSDoc** (TypeScript `/** … */`), placed on the symbol they document.
- **Single-line comments** (`#` or `//`) are for an inline note next to a non-obvious statement.
- **Do not stack single-line comments.** If a thought needs more than one line, use a docstring or JSDoc on the nearest symbol. No decorative section-header comments.
- **Be declarative.** Describe what the code is or does, not what it used to do, what it could do, or why an alternative was rejected; that belongs in commit messages, PR descriptions or design docs.
- **No ticket, issue or spec numbers in comments.** Describe the behavior or constraint in plain language.

```python
def month_range(start: str, end: str) -> list[str]:
    """Inclusive list of 'YYYY-MM' months from `start` to `end`."""
```

# Project Structure

PolicyHuis is a monorepo: a single agent that answers housing-policy questions for San Francisco and Amsterdam, with cited answers, through independent MCP servers. See the [README](./README.md) and the [MVP Technical Plan](./docs/plans/mvp-technical-plan.md). Directories other than `docs/` are planned and created as the work starts.

| Directory | Language | Contents |
|---|---|---|
| `backend/` | TypeScript | The backend: the question API and the agent loop |
| `browser-app/` | TypeScript, React | Web app: asks questions and shows streamed, cited answers |
| `protocol/` | TypeScript | The API between the backend and the browser app, including the citation schema the browser renders |
| `shared/mcp-kit/` | TypeScript | Optional helpers for MCP servers: formats, the tool errors (`UnknownValue`, `DatabaseUnavailable`, `DataUnavailable`) and the mapping of database failures to them, citation ID construction |
| `shared/node-config/` | TypeScript | Library every TypeScript node uses to read its configuration: YAML files decoded with a `Schema`, the `.env`-first provider, and `ConfigFileError` for anything missing |
| `shared/ingest/` | Python (uv), dbt | Library: fetch, archive and load public sources into a raw schema; shared dbt macros; run dbt |
| `shared/legal-text/` | TypeScript, Python | Legal-text MCP server, passage pipeline and its migrations; one codebase, run once per corpus |
| `san-francisco/housing-server/` | TypeScript | The `sf-housing` MCP server: San Francisco's housing pipeline and climate-zone tools |
| `san-francisco/ingest/` | Python (uv), dbt | San Francisco's `sources.yaml`, `raw_sf` migrations and `sf` dbt models |
| `san-francisco/legal-text/` | YAML | San Francisco's corpus and deploy settings for its legal-text instance |
| `netherlands/` | | The Dutch nodes, in the same shape |
| `evaluation/` | YAML / Markdown | Question set and expected answers |

**Each node runs on its own device.** Shared code is a library each node installs (a uv path dependency with its own lockfile, or a yarn workspace package), never a service a node calls. A city project depends on `shared/`; `shared/` never depends on a city, and no city depends on another.
| `docs/plans/` | Markdown | Technical designs. Read the relevant plan before changing a component. |

Contexts communicate through published contracts (database schemas, MCP tools and their results, the backend API), never by importing each other's code. MCP servers share nothing with the backend but MCP itself; `protocol/` is shared only by the backend and the browser app, and holds only schemas. No MCP server reads another server's schema. See [Domain-Driven Design](./docs/domain-driven-design.md).

## Python (`shared/ingest/`, `*/ingest/`)

- Manage dependencies with `uv` (`uv sync`, `uv run …`, `uv add …`). Never `pip install` into the project.
- Lint and format with `ruff`; test with `pytest`. Run `uv run ruff check . && uv run ruff format --check . && uv run pytest` before finishing a change.
- Integration tests run against a throwaway Postgres testcontainer started for each test session; they need Docker running. Never run them against a real database: they reset the schema.
- Settings are read from the project's own `.env` (for example `san-francisco/ingest/.env`), which takes priority over the shell, so other projects' variables (`DATABASE_URL`, `AWS_PROFILE`) can't leak in. Object storage uses only the project's own settings, never ambient AWS configuration.
- Migrations for the `raw_*` and `policy_text_*` schemas are Alembic with raw SQL, sequential ids (`uv run alembic revision -m "…" --rev-id 0005`) and are append-only once applied. Only the database owner runs them.
- Loaders archive each downloaded file, then parse the archived copy into `raw_*`, writing the manifest row and data rows in one transaction. Row filters (such as filtering a nationwide dataset to one city) live in the city's `config/sources.yaml` and are recorded in the manifest.

## TypeScript (`backend/`, `browser-app/`, `protocol/`, `shared/`, city servers)

- Follow [Effect Style](./docs/effect-style.md) and, for the web app, [Front-end Code Style](./docs/front-end-code-style.md).
- Manage workspaces with `yarn` (Yarn 4 through corepack: `corepack enable`, then `yarn install` at the repo root). Lint and format with ESLint and Prettier; test with `@effect/vitest`. Run `yarn lint && yarn format:check && yarn typecheck && yarn test` before finishing a change.
- **Never edit `yarn.lock` by hand**, and never hand-edit dependencies in a `package.json`: add, remove and upgrade them with `yarn add` / `yarn remove` / `yarn up` (`yarn workspace <name> add <pkg>@<version>` for one workspace), and let Yarn write the lockfile.
- TypeScript runs directly on Node's type stripping (`node src/main.ts`), so use only erasable syntax (no enums, namespaces or parameter properties); `tsc` only typechecks.
- Import `@effect/platform-node` modules by path (`@effect/platform-node/NodeRuntime`): its index also loads the Redis module, which needs the optional `redis` package.
- Server tests run against a throwaway PostGIS container (`imresamu/postgis:17-3.5`), so Docker must be running.
- Use Effect 4 (`effect` 4.x, AI modules under `effect/ai`). Model access goes through a config layer, not conditional imports.
- Validate with Effect `Schema`, not Zod.
- The `app` schema is defined with Drizzle in `backend/src/db/schema.ts`. Run `yarn workspace @policyhuis/backend db:generate` after changing it, which writes a SQL migration to `backend/drizzle/`; the backend applies pending migrations at startup. Applied migrations never change. **Never write or edit a Drizzle migration by hand**: every migration is exactly what `drizzle-kit generate` writes. If a generated migration cannot run (for example, a column type change Postgres cannot apply), stop and ask; the fix is to delete the unapplied migration, change `schema.ts`, and have the database owner drop and recreate the schema, never custom SQL.
